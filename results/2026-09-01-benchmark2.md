# Benchmark 2: does switching beat any fixed policy? 2026-09-01

Host: Lambda A100 (A100-SXM4-40GB, AMD EPYC 7J13, 30 vCPU), Ubuntu 24.04.2,
kernel `6.14.0-27-generic`, driver 580.173.02.
Serving: vLLM 0.28.0, `Qwen/Qwen2.5-0.5B-Instruct`, pinned to CPUs 0-3.
Antagonist: 8 CPU-bound processes pinned to the same cpuset.
Both vLLM and the antagonists run under the AKTS `sched_ext` scheduler in
`SCX_OPS_SWITCH_PARTIAL` mode; nothing else on the machine is affected.

## Correcting the mechanism first

The design document attributes the expected win to "preventing KV-cache
allocation stalls". KV-cache allocation is vLLM's own GPU-memory bookkeeping in
userspace; `select_cpu` has no influence over it. The measured mechanism is
different and much simpler: CPU contention delays vLLM's request handling,
tokenisation and prefill scheduling, which inflates time-to-first-token.

That precondition was verified before building the benchmark, since without it
there is nothing for a scheduler to fix:

| | no antagonist | with antagonist | factor |
|---|---|---|---|
| steady-state TTFT p99 | 27.0 ms | 308.0 ms | 11.4x |
| burst TTFT p99 | 120.5 ms | 406.2 ms | 3.4x |
| requests served during burst | 2593 | 544 | 4.8x fewer |

TTFT is the metric rather than end-to-end latency: end-to-end is dominated by
GPU decode, which CPU scheduling does not control, and would mask the effect.

## Why two objectives are needed

Measured under contention, the latency policy beats the throughput policy on
TTFT in every phase. If TTFT were the only metric, the latency policy would
dominate and switching could not help -- there would be no trade to make.

The antagonist is doing real work, so batch throughput is the second axis. The
question becomes whether switching can capture most of both.

## Arms

| Arm | Policy schedule |
|---|---|
| `static_latency` | slot 0 throughout |
| `static_throughput` | slot 1 throughout |
| `akts_switching` | slot 1 in steady state, slot 0 during the burst |

Workload: steady (concurrency 2) -> burst (concurrency 32) -> steady, 8 s each.

## Results

| | static_latency | static_throughput | **akts_switching** |
|---|---|---|---|
| steady_pre TTFT p50 | 82.0 ms | 284.2 ms | 281.1 ms |
| steady_pre TTFT p99 | 238.7 ms | 323.1 ms | 351.7 ms |
| **burst TTFT p50** | **238.4 ms** | 355.1 ms | **239.2 ms** |
| burst TTFT p99 | 386.6 ms | 395.9 ms | 401.1 ms |
| **burst requests served** | **1089** | 736 | **1086** |
| steady_post TTFT p50 | 85.8 ms | 281.6 ms | 287.6 ms |
| **total batch work** | 1.79 Mit | **1.99 Mit** | **1.93 Mit** |
| failed requests | 0 | 0 | 0 |

**Neither fixed policy is best on both objectives.** The latency policy gives
the best TTFT but retains only 90% of the batch throughput; the throughput
policy gives the most batch work but 49% worse burst TTFT p50 and serves 32%
fewer requests during the burst.

**Switching captures most of both.** During the burst, AKTS matches the latency
policy to within noise -- 239.2 ms vs 238.4 ms p50, 1086 vs 1089 requests -- while
retaining 97% of the throughput policy's batch work (1.93 vs 1.99 Mit).

## Negative result: the tail does not move

The design document predicts a 20-35% reduction in P99 tail latency. That is
**not observed.** Burst TTFT p99 is 386.6 / 395.9 / 401.1 ms across the three
arms -- flat, with the switching arm marginally the worst of the three.

The benefit is real but it is in **median TTFT and request throughput**, not in
the tail. Under saturation the tail is set by queueing at the burst's
concurrency level, which policy choice does not change. The claim in the design
document should be restated accordingly.

## Caveats

- Switching is **oracle-driven**: the driver switches on known phase
  boundaries. This bounds what any online detector could achieve; it does not
  show that a burst can be detected in time. An agent-driven arm is required
  before claiming the end-to-end system works.
- Steady-state TTFT under AKTS is deliberately poor (281 ms p50), since the
  throughput policy is selected there. Whether that is the right trade depends
  on an SLO that this experiment does not define.
- Single host, single model size, one burst shape, one run per arm. No
  confidence intervals; differences under ~5% should not be read as real.
