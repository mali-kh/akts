# Feasibility probe — 2026-08-31

Host: `anrg-4` — Intel Core i3-N305 (8 cores), Ubuntu 24.04.2, kernel
`7.0.0-28-generic`, BTF present, `sched_ext` compiled in and `disabled`.

All tests below are **load-time only**. No scheduler was ever attached;
`/sys/kernel/sched_ext/state` read `disabled` before and after every run.

## Gate 1 — does `bpf_tail_call` verify inside a sched_ext `struct_ops` program?

**Yes.** Two controls bracket the result.

| Program | Result | xlated / jited |
|---|---|---|
| XDP + `bpf_tail_call` (control) | load succeeded | 48 B / 75 B |
| struct_ops, tail call removed (control) | load succeeded | 120 B / 73 B |
| **struct_ops + `bpf_tail_call`** | **load succeeded** | **176 B / 171 B** |

The jited size roughly doubles when the tail call is present (73 B -> 171 B),
consistent with the tail-call prologue being emitted.

## Gate 2 — can a sched_ext `struct_ops` program be inserted into a `PROG_ARRAY`?

**Yes**, with a caveat. Prog-array entries must match `prog_type` *and*
`attach_btf_id`, and sched_ext programs bind their `attach_btf_id` to a specific
`sched_ext_ops` member, so gate 1 does not imply gate 2.

    jmp_table: key 0 -> prog id 86242

libbpf refuses to load a `SEC("struct_ops")` program that no struct_ops map
references (`"program isn't referenced anywhere"`, `-EINVAL`). This is a
userspace restriction, not a kernel one. Worked around by declaring a second
`sched_ext_ops` map on the same `.select_cpu` member purely so the policy
program is loaded; that map is never registered.

## Benchmark 1 — actuation latency

Cost of applying a policy change *after* the decision is made. n=200,000
(AKTS arm) and n=20,000 (baseline arm), warm.

| Arm | mean | p50 | p99 | max |
|---|---|---|---|---|
| AKTS slot swap (`bpf_map_update_elem`) | 465 ns | **447 ns** | 731 ns | 23.1 us |
| Baseline A: `/proc/sys` write (LumOS-style) | 533 ns | **533 ns** | 570 ns | 4.9 us |

**Parity, not a speedup.** Both arms are a single syscall. This is the intended
result: AKTS retains knob-tuning actuation cost while gaining the ability to
switch whole policies. The large win is against Baseline B (SchedCP-style
recompile + verify + reload), which is seconds to a minute and is not on the
same timescale.

## Agent decision latency (context for end-to-end numbers)

`llama3.2:3b` via ollama on the same CPU class (`anrg-3`, i3-N305, no GPU),
prompted for a single-digit policy choice, `num_predict=4`, `temperature=0`:

| | latency |
|---|---|
| cold start (first call) | 11,664 ms (model load 10,230 ms) |
| warm, p50 | 403 ms (fixed overhead 255 + prompt eval 72 + generate 71) |
| compute only | ~145–200 ms |

All five trials returned `0`, correctly and deterministically, for
`p99_latency_ms=18.4, cpu_util=0.82`. Qwen-2.5-0.5B was not available and
remains unmeasured; the design assumes ~100 ms for it, which is optimistic but
the right order of magnitude given the fixed framework overhead above. The
11.7 s cold start means the agent must stay resident.

## Open

- **Gate 3 — untested.** Load-time acceptance does not prove the tail call
  actually dispatches at runtime through a struct_ops trampoline. Testable
  without a sched_ext attach by using `tcp_congestion_ops` on a single socket.
- **Out-of-range index behaviour — untested.** Writing an unpopulated slot index
  should fall through to the dispatcher's default return. This is the direct
  test of the "agent hallucinates a nonsense choice" safety claim.
- **Workload evaluation — not started.** Requires root and a GPU on the same
  machine; no node in the anrg cluster has a GPU.
