# Gate 3: runtime dispatch, and behavior under an invalid index

Host: Lambda A100 instance, AMD EPYC 7J13, Ubuntu 24.04.2, kernel
`6.14.0-27-generic`.

## Why this needed its own experiment

Gates 1 and 2 established that a tail call inside a struct_ops program passes
the verifier, and that a struct_ops program can be installed into a
`PROG_ARRAY`. Neither shows that the tail call **transfers control** at run
time. A `bpf_tail_call` that fails does not raise an error: it simply returns,
and execution continues at the next instruction. From the outside that is
indistinguishable from success.

The dispatcher is therefore instrumented on both paths:

    counters[0]  incremented on entry                -> dispatcher ran
    bpf_tail_call(ctx, &jmp_table, slot)
    counters[1]  incremented inside the policy module -> DISPATCHED
    counters[2]  incremented after the tail call      -> FELL THROUGH

`counters[1]` and `counters[2]` are mutually exclusive per invocation, so the
two outcomes can be told apart rather than inferred.

## Vehicle

`tcp_congestion_ops` rather than `sched_ext`. It is the same struct_ops
trampoline mechanism, but it is driven by an ordinary loopback TCP transfer and
a malformed program cannot make the machine unschedulable. The struct_ops link
is owned by the loader process, so the algorithm is unregistered automatically
if it exits.

## Results

48 MiB over loopback per run.

| Active slot | Dispatcher entered | Policy entered | Fell through | Transfer |
|---|---|---|---|---|
| 0 (populated) | 766 | **766** | 0 | 48 MiB OK |
| 7 (never populated) | 771 | 0 | **771** | 48 MiB OK |

**Gate 3 passes.** With a valid index the tail call dispatched on every single
invocation -- 766 of 766, no fall-throughs. Dispatch is not merely usually
successful; it is exact.

**Invalid index degrades safely.** Pointing the dispatcher at an empty slot
produced 771 fall-throughs and zero dispatches. The TCP transfer completed
normally, no kernel errors were logged, and load average stayed at 0.00. The
tail call is a no-op when the slot is empty, so control continues on the
dispatcher's default path.

## What this establishes

- The mechanism works end to end: verifier, map population, and runtime
  dispatch.
- The failure mode for an out-of-range agent decision is **falling back to
  default behavior**, not a crash and not undefined behavior. Combined with
  the fact that every reachable slot was verified at load time, an agent
  emitting an arbitrary integer cannot produce an unsafe kernel state -- only a
  suboptimal or inert one.

## Confirmation on sched_ext proper

The `tcp_congestion_ops` result above establishes the general struct_ops
mechanism. The same experiment was then repeated on a real, attached `sched_ext`
scheduler, removing that caveat.

The scheduler is attached with `SCX_OPS_SWITCH_PARTIAL` and `timeout_ms=5000`,
so only tasks explicitly moved to `SCHED_EXT` are managed by it; the rest of the
system stays on the default scheduler. The struct_ops link is owned by the
loader process, so the scheduler detaches if that process exits. Load is eight
workers alternating compute and a short sleep, so `select_cpu` is exercised on
every wakeup.

| Active slot | Dispatcher entered | Policy entered | Fell through | Workers |
|---|---|---|---|---|
| 0 (populated) | 64,160 | **64,160** | 0 | 8/8 completed |
| 7 (never populated) | 60,217 | 0 | **60,217** | 8/8 completed |

**Gate 3 passes on sched_ext.** Exact 1:1 dispatch across 64,160 invocations,
two orders of magnitude more samples than the TCP vehicle, with no
fall-throughs.

**The invalid index remains inert.** All 60,217 invocations fell through to the
dispatcher's default path, which calls `scx_bpf_select_cpu_dfl` -- i.e. the
system reverts to stock CPU-selection behavior. All eight workers completed,
`dmesg` logged no panics, oopses or BUGs, and `sched_ext` returned to `disabled`
on detach.

## What this establishes, restated

An agent whose only output is an integer cannot produce an unsafe kernel state.
A valid index dispatches deterministically; an invalid one is a no-op that falls
back to default scheduling. Both outcomes were measured on an attached
scheduler, not argued from the design.
